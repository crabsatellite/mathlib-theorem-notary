实现分支 `notary/erdos848-v0` 固定在 mathlib `54e71fa9173471d591658f5380c46aaf050bbaae` / Lean `v4.30.0-rc2`，与 #848 已有内核归档兼容。第 7 节较新上游快照用于源码调研，不是本案例运行版本。运行入口见 [Notary/README.md](../Notary/README.md)。

## 1. 目标与信任语义

任何人都可以提供并发布一个公开、可审查、可重放的 kernel-only 定理组件。发布签名记录 provider credit，即“该密钥持有人提供了这个精确版本的组件”，不构成数学背书，不给予签发者增加公理、放宽检查或创造定理的权限。多人签名是多个提供者记录，不是以投票决定命题成立。

数学有效性来自固定基础上的内核检查。协议把这个结果变成可以定位、分发、导入和复用的组件，同时保留完整 Glass Box 内容。

本协议采用 Engineering Layer 正文的两个定义：

- Kernel-only closure：精确端点及其承重依赖完整可检查；无未完成证明、项目专用公理或未经检查的外部结果；固定检查器、源码闭包、版本和允许逻辑基础，并有完整重放。
- Glass Box：日常使用窄接口，内部证明、证明地图、依赖图和检查器仍可取得并独立重放。

一个人可以用自己的私钥签任何字节；协议不能禁止这种行为。协议控制的是哪些对象能够通过组件验证和进入合格的发布、构建、导入状态。签名有效不能直接产生“已验证”状态。

## 2. 三种对象必须分离

| 对象 | 内容 | 是否决定数学检查结果 |
|---|---|---|
| Component core | 精确声明、定义及证明闭包、逻辑基础、公开源码与重放配方、许可 | 决定被检查的对象 |
| Build realization | 某次构建的工具链、平台、输入清单、全部产物摘要、与组件的绑定 | 决定此次实际读取哪些字节 |
| Credit record | 提供者公钥、组件与发布包身份、角色声明、来源/派生关系、签名 | 不决定数学正确性 |

此外有本机 verification record：由本机受控验证器产生，绑定实际检查对象、基础、检查器和策略。它不是提供者签名的另一种叫法，也不因来自远端就自动有效。

三个内容身份按规范化编码和有域分隔的密码学摘要分别生成。v0 已实现带域分隔的 SHA-256 身份与 Ed25519 credit。签名本身不进入 component core 的身份。通用协议应将可变镜像地址移出核心；当前 #848 固定适配器仍将不可变来源地址纳入核心，变更它会改变该 v0 身份。具体序列化规范必须有跨实现测试向量。

另设接口指纹，覆盖声明类型、宇宙参数和引用定义环境。接口指纹不宣称识别数学等价定理。相同接口的不同证明可以是不同组件；不得凭显示公式相同合并它们。

提供者签名不自动证明自然人身份、原创权、优先权或作者资格。作者、形式化者、打包提供者和镜像运营者分别记录，并保留上游许可与归属。

## 3. 最小公开组件

组件必须具有以下可取得的内容，而不仅是链接或成功日志：

1. 精确公开端点：模块、声明名、完整类型、宇宙参数，以及类型所用定义的身份。
2. 数学证明对象及其传递依赖。完整证明部分不能被裁掉而仅保留接口或序列化后的 axiom 占位视图。
3. 可读 Lean 源码、必要的生成源码/有限证书、构建配置、锁定依赖、工具链与重放说明。大型生成器的搜索过程可以不属于演绎信任基础，但实际使用的证书和检查器必须公开。
4. 固定逻辑基础及实际使用的公理清单。允许公理按完整声明与基础身份核对，不能只允许几个名字；重定义成其他类型的同名公理必须被拒绝。
5. 证明与定义闭包、构建输入、产物的密码学摘要。v0 可保守绑定完整模块及锁定源码包；精细到声明的裁剪属于后续优化。
6. 人类声明、语义映射、证明地图、许可和维护/勘误信息。内核验收仅针对形式声明，不能把这些文字自动标成已机器证明。

数学闭包与构建闭包分别记录：用于生成证明的 tactic、工具和编译输入可能远大于最终证明项的依赖。构建工具中的 unsafe 实现不因出现这个词就导致数学失败；检查器必须判断实际承重证明依赖。

v0 接受固定官方 Lean 基础中的标准公理，并核对类型及基础版本。自定义公理、sorryAx、依赖未经内核验证原生计算的额外公理，不属于该 kernel-only profile。允许非标准基础的后续 profile 必须明确命名，不能沿用同一个合格状态。

源码与二进制的对应也要单独记录。直接重放一个公开证明对象，可以验证该对象的形式数学；这不自动证明它确实由所列可读源码构建而来。发行方应提供可重建配方；审查端用重建后的声明/证明内容对齐核查对应。存在不确定性时分别报告“证明对象已检查”和“源码对应尚未独立重现”，不能用签名消除差别。不同平台的产物不强求逐字节相同，而是作为不同 realization 分别检查。

## 4. 发布和消费的状态机

发布流程：

```text
公开输入与声明
  -> 固定输入快照
  -> 构建实际证明产物
  -> 内核重放 + 精确端点/逻辑基础/闭包检查
  -> 封装固定组件与 build realization
  -> 提供者签署 credit record
  -> 上传公开对象
  -> 发布服务核对公开可得性与对象，并执行自己的准入验证
  -> 可检索发布记录
```

签名使用独立的发布步骤。运行第三方构建脚本的阶段不需要接触发布私钥。发布服务可以自行核验，结果作为可检查记录展示；它的结论不是下游内核的替代品。上传候选对象和取得合格状态是两个动作；暂未完成核验的对象保持候选状态。

消费流程：

```text
锁定组件身份、端点、基础、realization 和验证策略
  -> 获取对象并核对全部摘要/credit 归属
  -> 检查本机已有验证状态是否精确匹配
       命中：复用本机已检查结果
       未命中：检查尚未检查的证明闭包
  -> 本机验证器产生已检查状态
  -> 将对应的真实定理声明/产物提供给下游构建
  -> 检查下游端点及实际引用的组件
```

最重要的不变量：消费端不能通过 `signature_valid -> P`、`axiom importedTheorem : P` 或等价机制把提供者归属转为数学事实。引入的必须是实际经过适用验证流程的定理对象。

普通 `import` 可以继续使用。网络解析、下载、签名核对与验证调度发生在构建层，不在 Lean 类型检查过程中联网。离线构建依赖锁文件和已取得对象。

## 5. 初次验证与重复构建

在“提供者签名不提供数学背书”的约束下，全新消费者不能只检查签名就获得内核检查结论。严格路径需要首次检查证明闭包，随后复用本机建立的验证状态。

这能避免重复证明搜索、重复 elaboration，以及同一主机同一固定闭包的重复检查，但不保证消除首次 kernel replay、证明读取和存储成本。签名不会自动压缩证明。

验证缓存至少绑定：组件数学身份、实际产物摘要、完整依赖身份、基础/公理 profile、检查器实现与版本、验证器策略版本和完成状态。内容不变且检查契约不变时，经过时间本身不使记录失效。发现影响适用版本的检查器缺陷或修正验证策略时，可以明确使相关记录失效。

普通 Lake freshness trace 只能帮助调度，不能授权数学验收。本机验证状态必须由受控验证器写入；只读输入、原子完成、独占执行/检查后复用和输入不变性检查防止竞争或构建过程中漂移。证明包不能通过提供一个自写 JSON 缓存文件把自己标为已验证。

第一阶段使用完整冷重放作为正确性基线。第二阶段才实现“已检查的依赖 + 新增声明”的增量检查：所有引用必须落在本机已验证、身份匹配的基础里，未覆盖引用一律失败。互递归定义、归纳类型与构造器/递归器按合法原子组处理，不假装所有声明天然形成普通 DAG。

换署名、增加 mirror、补充非承重文字不会改变数学验证结果。改变证明、定义、假设、依赖、检查器或验收 profile 时，按实际受影响的范围重新检查。源码变化但证明对象相同时，数学验证可复用，源码对应检查仍应更新。

## 6. 发布中心的职责

中心提供内容寻址存储、检索、镜像发现、版本和派生关系、公开可得性检查、可选的独立重放服务、署名与勘误记录。任意密钥持有人均可提交合格组件，无需教授身份或 mathlib 维护权限。

注册状态与消费者本机验证状态分别显示。中心的上传资格、流量配额、存储治理不能被解释为数学权威。协议应允许多个兼容中心和离线对象交换。

版本名称可以更新，已签对象保持固定。源码或证明不再公开可得时，记录“公开可得性失败”；本机已有且检查过的证明不因此变为假。提供者撤回 credit 或密钥失效改变归属记录的状态，不撤销已经通过检查的数学推导。语义映射错误、声明修订、检查器缺陷分别有各自的勘误影响范围。

### 7.1 推荐的第一版

先做一个普通 Lean/Lake 扩展包和独立验证器，固定支持一版工具链。mathlib 作为可锁定依赖和首个大规模测试生态。先验证包级/模块级完整闭包，再优化到声明级边界。

提供者在工程配置中声明导出端点；客户端在锁文件中固定组件。自定义 Lake 目标完成构建、公开对象清单生成和验证。下游库用 `needs` 显式依赖外部组件验收目标；项目合格发布目标覆盖最终端点检查。不能只加一个默认不执行的 lint，也不能只在 `post_update` 时检查，因为产物在之后仍可能变化。

v0 不修改内核的推理规则，不把签名验证纳入逻辑基础，也不要求将组件并入 mathlib 主库。只有原型证明现有扩展点无法保证必要的构建/导入顺序时，才考虑针对 Lake 或 Lean loader 的小范围改动。

可能的命令外观如下，均为拟议接口，不是现有命令：

```text
lake build componentPackage        # 构建、导出、验收组件包
lake exe component credit PACKAGE  # 仅对验收过的固定发布包生成提供者归属
lake exe component publish PACKAGE # 独立的外部发布动作
lake build Consumer                # 依赖组件验收，本机检查命中则复用
```

组件验收和下游产物需要精确绑定实际使用的所有 `.olean` 数据部分。当前 module system 区分 exported/server/private 数据；只拿 exported 接口可能看不到证明体。也要区分数学证明检查与构建时动态库、插件、初始化代码的执行。验证阶段按固定工具链的数据读取路径进行，未经验证的原生扩展不能进入验证器执行环境。

模块/包适配器仍受 Lean 的命名空间、工具链版本和依赖一致性约束。v0 遇到同名不同定义或不兼容依赖时拒绝，不自动把定义等同或重命名。跨工具链/跨证明助手的转换须产生新的受检实现或明确的受检转换，不以原签名证明兼容。

### 7.2 现有缓存不等于这个协议

当前 mathlib Cache 安全文档明确以来源信任隔离为主，输入缓存键不等于产物字节身份。`Cache/Hashing.lean` 的键和 Lake `Build.Trace.Hash` 使用 `UInt64`；Lake 源码也留有改用安全哈希的 TODO。因此协议要另建密码学对象摘要，保留现有 trace 做构建优化。

Lean 的 replay 允许添加 axiom declaration。因此 replay 成功必须结合精确基础/公理闭包检查，不能单独等同于本协议的 kernel-only 合格状态。最新 `collectAxioms` 会复用导入元数据，独立验收必须从完整、已检查的声明重算或验证其覆盖性。

### 7.3 与现有 Paper Infrastructure 的复用边界

现有 verification receipts 已有固定输入、前后漂移检查、独占执行、原子记录和 run-or-reuse，可以复用这些调度设计。

但当前 `verification_receipt.py` 使用主机秘密上的 HMAC-SHA256。它适合本机/受控主机域的执行记录，不是任何人都能以公钥核验的公开 credit 签名。公开协议应另加非对称 credit 对象，不公开主机秘密，也不改变现有收据的信任含义。通用命令退出码和输出 token 检查同样不能替代专用的 Lean 端点/闭包验证器。

## 8. 必须验证的协议性质

下面列出协议要求；其逐项证据与仍未实现部分见第 13 节，不能将目标清单本身视为完成证明：

1. Credit-independent acceptance：换一个有效提供者签名或增加签名，不改变固定证明对象的数学验收结果。
2. Exact binding：被验收的端点类型、定义环境和最终导入对象与锁定组件一致。
3. Closure completeness：实际承重引用全部落在已检查闭包和固定逻辑基础中，无隐藏项目公理。
4. Incremental equivalence：有效缓存命中的增量检查，与对同一声明集合和基础的完整重放给出同一验收结论。
5. No signature-to-theorem rule：签名不会在内核环境里生成新的数学假设。
6. Replayability：取得完整公开包的第三方，可以按固定配方重做验证，不需要提供者或中心的私钥。

若将这些性质写成形式化命题，需要先固定输入语言、内核模型、摘要/文件系统假设和验证状态迁移语义。不能仅凭 schema 校验或测试通过声称完整协议已证明安全。

## 9. 原型验收与性能问题

先使用很小的有效组件和一个消费项目，进行有辨识力的验收：

| 场景 | 预期 |
|---|---|
| 同一组件由两个不同密钥提供 | 两者数学验收相同，credit 分别记录 |
| 有效签名、公开源码，但目标使用 sorry/项目公理 | 拒绝 kernel-only 验收 |
| 只改目标的一个假设或一个同名定义 | 原组件绑定失败 |
| 改 proof/olean 字节，沿用输入缓存键和旧记录 | 拒绝复用；重新检查或失败 |
| 上游依赖含未披露公理，表面报告为空 | 独立闭包检查拒绝 |
| 丢失 private proof 部分或仅保留接口占位 | 完整证明模式失败 |
| 伪造 imported axiom 元数据、构造器、递归器 | 对应检查失败 |
| 依赖/工具链/策略改变 | 原验证记录不授权新对象 |
| 构建或验收中途修改输入、并发抢同一缓存 | 不产生已完成状态；执行受控 |
| 同一机器第二次构建相同下游 | 复用匹配记录，不重跑昂贵验证 |
| 完全新机器只有提供者签名 | 不能跳过首次数学检查 |
| 更新署名、镜像，或更换 provider key | 数学组件可继续复用，归属记录单独更新 |

性能实验应分别测量证明生成、elaboration、内核重放、摘要扫描、反序列化、冷下载、热构建、峰值内存和存储量。#848 案例复用精确历史归档，不重新生成大型证明；新消费者通过受控 run-or-reuse 执行。多层攻击使用独立的小型真实 Lean 模块。

核心研究问题是：能否在保持上述验收性质的条件下，把重放和加载成本按已检查闭包有效分摊。窄接口本身不保证内核可以完全不加载相关定义和证明数据。若首个实验显示瓶颈主要是首次重放或巨量数据加载，再研究声明分区、检查后的持久环境、证明压缩与精简导出；不能以改用任意人的签名来掩盖该成本。

## 11. 声明级证书与多层引用

仓库是发布容器，不是证书粒度。每条可检查 theorem 都可作为独立出口，不要求它是仓库的主定理。同一模块的多个出口共用源码、olean 和基础身份，各自绑定声明名、结构化类型和宇宙参数，分别取得 credit；提供者不能将 A 的签名移用到 B。

`#notary_inspect` 从实际 Lean 环境选取 theorem，而不是采用提供者填写的显示字符串。8 层真实构建例子在每层导出 `identity` 和 `successor`，形成 16 张独立证书。#848 消费目标检查 `all_N` 和 `tailClose` 两个真实出口；现有归档适配器的已签公开主记录仍为 `all_N`，额外出口的结构化检查报告输出到本机状态目录。

每个结论证书绑定精确依赖证书 ID，形成内容寻址的引用图。消费者另持锁定的根 ID 和基础策略；它们不能从本次下载的图自动提升为信任根。验证器遍历每一条传递边，检查节点签名与身份、实际源码及 olean 摘要、同名模块冲突和基础一致性。共同依赖只核对一次。修改中间字节会使原锁定对象失配；修改成另一条正确证明可以产生新证书，不能沿用旧身份。

密码学保护的是对象身份与归属，不能证明“依赖清单已经完整”或“内核确实检查过”。`notary_chain.py` 的成功字段明确为 integrity verified，同时数学准入仍为 requires-host-kernel-receipt。实际导入还需要受控构建捕获完整加载闭包、隔离搜索路径，并核验每个未覆盖的依赖。当前真实多层夹具由主机生成并检查全部依赖；它不冒充任意外来包的通用准入器。

## 12. 敌对设计与已保留的边界

- 换中间源码、olean 或声明：旧 ID 或文件摘要失配，拒绝。
- 重签整个假图：旧消费者根不存在，拒绝；下载方无权更新消费者锁。
- 同名模块的不同字节争用搜索路径：拒绝。不同结论共享同一模块字节：允许。
- 提供者自写 kernel_verified、伪造成功 JSON：不构成准入依据；未知保证字段拒绝。
- sorry、自定义公理、将 axiom 冒充 theorem、错误证明：真实 Lean 与额外公理检查拒绝签发合格的夹具证书。
- 元数据文本假称 valid：`#notary_info` 显式标为展示文本；数学和签名状态由外部验证器决定。
- 合法签名者重写源码和整个证明包：新内容仍需独立内核验收，签名不能解除该要求。

尚不能宣称解决任意恶意 Lean metaprogram / native plugin 的进程隔离、恶意编译器或主机、可写存储的所有 TOCTOU 竞争、网络中心的可用性与撤回治理。完整服务需要隔离构建进程、受控独立检查器、只读内容仓、工具链供应链身份和可验证的加载闭包；本 v0 不把这些未实现能力记为通过。

## 13. 声明交换 v1 与贡献界定

v1 的 [固定规范](../Notary/SPEC.md) 明确公开包、声明证书、提供者 credit、消费者锁、序列化与摘要域。每个父包绑定依赖的包 ID 和声明证书 ID；不是只锁仓库地址或可变分支。完整证明与源码闭包随包提供，多个结论共用字节但分别签名。跨语言向量由 Python 与 Node.js 分别计算和验签。

`Notary/Verifier.lean` 从干净的工具链搜索路径启动，之后只以数据方式加载包，禁用导入扩展和外部插件。它向新内核环境重放实际声明，遍历真实常量依赖，并将每一层证书的类型、宇宙参数和允许公理与实际结果比较。官方基础的同名遮蔽被拒绝；依赖中藏着一张假的结论证书，也不能通过重签外包来洗白。它使用 Lean 原有内核和二进制读取器，不是第二套独立实现的逻辑内核，也不是内存安全沙箱。

`Notary/Composition.lean` 对有限验收推导证明任意深度组合的健全性，并证明数学验收与 credit 无关。前提是固定基础健全、局部推理检查健全且依赖绑定准确。三个定理不依赖公理；这不证明 Python、摘要、签名算法和文件系统正确。实现将包裹深度限制为 64 层以控制资源，与数学定理没有固定层数上限是两回事。

[复现实验](../Notary/REFERENCE.md) 使用二叉树的镜像复原和叶子计数两条不同结论，再由两个后续项目实际消费、导出新结论。普通默认 `lake build` 必须经过依赖准入；篡改后不得留下成功状态。冷实验只传公开包，消费者持新密钥和新状态；目前是同机独立进程，不能写成已有外部研究者或另一物理机器复现。实验将普通 Lake 冷/热构建、摘要验签、独立重放、复用和依赖更新分别记录。

现有 Lean 导入、独立环境检查器、OpenTheory 理论包以及 in-toto 供应链证明都是相关先例。新增价值是面向 Lean 定理交接的精确声明身份、无背书的 credit 语义、全层引用绑定和验收复用契约，以及这些规则的可执行组合。不能将“能导入外部定理”本身写为新发现。[相关工作与价值分析](../Notary/RELATED_WORK.md) 给出已核查的正式论文及能力对照。

本实现面向已证明组件的交接、来源审查和重复验收，不能补齐缺失数学证明，也不能自动保证自然语言定理与形式端点一致。当前按完整闭包保守重放，不主张获得声明级增量速度收益。后续最有辨识力的证据是第二个真实大型案例、独立使用者复现和相同保证条件下的成本比较。
